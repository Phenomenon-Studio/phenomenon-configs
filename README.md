# phenomenon-configs

Shared configs, project template and CI for Phenomenon Studio frontend projects. A fix lands here once and reaches every project as a versioned update: a package bump, a template update PR or a moved workflow tag. Nobody copies and pastes it.

| Stack | Starter | Source template |
| --- | --- | --- |
| `vite` | React SPA, TanStack Router + Query + Form, shadcn/ui, Tailwind v4 | `Phenomenon-Studio/admin-template` |
| `next` | Next.js App Router, TanStack Query, CSS Modules | `Phenomenon-Studio/phenomenon-next-ts-template` |

## Create a project

Requires Node 24+, pnpm, [uv](https://docs.astral.sh/uv/) (`brew install uv`) and read access to GitHub Packages (`echo "//npm.pkg.github.com/:_authToken=$(gh auth token)" >> ~/.npmrc`, token scope `read:packages`).

```bash
pnpm dlx @phenomenon-studio/create-app my-app             # asks for name and stack
pnpm dlx @phenomenon-studio/create-app my-app --stack next
pnpm dlx @phenomenon-studio/create-app my-app --stack vite --styling css-modules
# without the wrapper:
uvx copier copy --trust gh:Phenomenon-Studio/phenomenon-configs my-app
# pin a template release:
uvx copier copy --trust --vcs-ref v1.4.0 gh:Phenomenon-Studio/phenomenon-configs my-app
```

Commit `.copier-answers.yml`. It records the template release the project was generated from.

## Keep a project up to date

| What changed | How it reaches the project |
| --- | --- |
| A lint/TS/format rule, an ESLint or Prettier plugin | `@phenomenon-studio/*` package release → Renovate PR (patch/minor automerge) |
| A non-extendable file (`.gitignore`, hooks, `vite.config.ts`…) | Template release → weekly **Template update** PR (`copier update`) |
| A dependency version (react, next, vite, Node, pnpm…) | Project Renovate PR (shared preset) **or** the template update PR when the platform catalog moved |
| The CI pipeline | Picked up automatically on the next run (`node-ci.yml@v1`); majors need a template update |

Run an update by hand from the project root:

```bash
pnpm dlx @phenomenon-studio/create-app update      # = uvx copier update --trust --skip-answered
```

Copier does a 3-way merge. Local edits survive, and overlapping edits show up as `<<<<<<<` conflict markers. [docs/dependency-versions.md](docs/dependency-versions.md) covers how dependency versions flow.

## What lives where

Each file goes to the first channel that fits:

1. The tool supports `extends` or an import (ESLint, TS, Prettier, Stylelint, Commitlint) → **npm package** in `packages/`.
2. CI pipeline → **reusable workflow** in `.github/workflows/`.
3. Dependency policy → **Renovate preset** in `renovate/`.
4. Anything else → **Copier template** in `template/`, kept as thin as possible.

```text
copier.yml                       # template questions; Copier reads it from the repo root
template/
├─ versions.jinja                # dependency catalog: every version a generated project gets
└─ project/                      # rendered files (_subdirectory)
   ├─ …                          # shared by all stacks (.gitignore, husky, eslint.config.js, package.json…)
   ├─ {{ '.' if stack == 'vite' else '' }}/   # vite layer: merged into the root for stack=vite, skipped otherwise
   ├─ {{ '.' if stack == 'vite' and styling == 'tailwind' else '' }}/      # vite UI: shadcn/ui kit, sidebar, pages
   ├─ {{ '.' if stack == 'vite' and styling == 'css-modules' else '' }}/   # vite UI: CSS Modules kit, pages
   └─ {{ '.' if stack == 'next' else '' }}/   # next layer
packages/
├─ eslint-config/                # @phenomenon-studio/eslint-config      base · react · tanstack-query · tanstack-router · vite · next
├─ tsconfig/                     # @phenomenon-studio/tsconfig           base · react · vite · next · node
├─ prettier-config/              # @phenomenon-studio/prettier-config    default · tailwind
├─ stylelint-config/             # @phenomenon-studio/stylelint-config   default · tailwind
├─ commitlint-config/            # @phenomenon-studio/commitlint-config
└─ create-app/                   # @phenomenon-studio/create-app         npm wrapper around `uvx copier`
examples/                        # generated by Copier, committed, built in CI (workspace members)
├─ answers/<example>.yml
├─ vite/                       # stack=vite, styling=tailwind
├─ vite-css-modules/           # stack=vite, styling=css-modules
└─ next/
.github/workflows/
├─ node-ci.yml                   # reusable: lint · tsc · test · build (projects pin @v1)
├─ template-update.yml           # reusable: scheduled `copier update` → PR
├─ template-check.yml            # this repo: packages, example drift, example builds, upgrade test
├─ sync-examples.yml             # re-renders examples/ on Renovate branches
├─ release.yml                   # Changesets → GitHub Packages
└─ release-template.yml          # tag vX.Y.Z + move vX
renovate/default.json            # shared Renovate preset for projects
renovate.json                    # this repo's Renovate (extends the preset + catalog managers)
```

## Develop

```bash
pnpm install
pnpm test                  # package smoke tests (load each config, run the tool on a fixture)
pnpm examples:regen        # re-render examples/ from the working tree (needs uv)
pnpm check                 # lint · typecheck · test · build for every package and example
pnpm template:update-test vite   # render the last vX.Y.Z tag, copier update to HEAD, build
```

Examples are pnpm workspace members. They depend on `@phenomenon-studio/*` with the same pinned versions a real project gets, and `linkWorkspacePackages` resolves those to `packages/`. A rule change that breaks a stack therefore fails in the same PR.

Every template change must ship with regenerated examples. CI fails on drift.

### Rules for changes

- List every lint rule or TS strictness change in the PR description. Behaviour never changes silently.
- Prefer fewer `copier.yml` questions. Each one doubles what CI must cover.
- Tool versions are pinned here. Only `peerDependencies` of packages use ranges.
- `pnpm-workspace.yaml` enforces a 3-day `minimumReleaseAge`. `node scripts/pin-mature-versions.js <package.json>` pins newly added dependencies to the newest release older than that.

See [docs/releasing.md](docs/releasing.md) to ship, [docs/migrating.md](docs/migrating.md) to move an existing project onto the platform, [docs/audit.md](docs/audit.md) for how the original templates were merged, and [MIGRATIONS.md](MIGRATIONS.md) for breaking changes.
